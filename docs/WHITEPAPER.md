## 1. 项目简介与设计目标

### 1.1 LYSOR OS 是什么

LYSOR OS（凌霄）是一套面向 x86_64 平台的全新操作系统，使用 Rust 语言以 `no_std` 模式从零构建，不基于 Linux、BSD 或任何现有内核改写，以 MPL-2.0 许可证开源（含专利报复条款）。

它要回答的问题只有一个：**现有内核架构在"性能、安全、可验证、生态"四个目标之间互斥，没有一种主流架构能同时兼顾。**

LYSOR 的答案是自研**组件化混合内核（Componentized Hybrid Kernel）**：以最小可信基座为核心，把性能敏感与功能扩展子系统做成"内核内可选组件"——在同一地址空间内直调以获得宏内核级性能，同时用独立故障域与策略治理获得优于宏内核的隔离性。

### 1.2 当前已实现（经启动实测验证）

系统可在一台普通 QEMU 虚拟机上完成从引导、装机、使用到关机的全流程：

- **内核基座**：长模式引导、抢占式调度与栈金丝雀、物理/虚拟内存、内核堆分配器、双通道 IPC、系统调用、块设备抽象与 LFS 真盘持久化；
- **每进程独立地址空间**：独立页表根、内核区域对用户代码不可见、ring 3 执行模型、进程退出逐帧回收——应用越权的防线是硬件分页，不只是软件检查；
- **SMP 多核调度**：多核实测验证（每 CPU 独立运行上下文与本地中断控制器，核间中断驱动调度，自旋锁保护内核共享结构），单核运行无回归；
- **内核组件（KC）机制**：私有动态栈、独立故障域、持久化策略、完整故障处置链路；
- **双密码栈**：国密三算法（SM2/SM3/SM4，GB/T 32918/32905/32907）优先 + 国际备用轨（Ed25519/SHA-512，RFC 8032），全链路强制验签；
- **驱动 KC 化（开放端子）**：通用/Intel 显卡、USB、e1000 网卡驱动全部以内核组件形态注册运行，驱动管理器 + 内核导出表构成第三方 .lykc 驱动的唯一调用面，强制验签装载（fail-closed，无旁路）；
- **网络栈**：e1000 网卡驱动 + 协议栈（ARP/IPv4/ICMP/UDP/DNS/TCP 客户端/HTTP 客户端/**TLS 1.2 客户端**），QEMU user-net 环境联调上电，网关/DNS 自动配置；TLS 端到端冒烟 `tls: E2E OK bytes=175` 已通过；
- **IQCL 账号登录**：桌面登录屏（本地账户直达 / IQCL 设备码流程），会话持久化免重登，level ≥ 100 判定开发者；
- **应用安装签名门**：.lyx 装载器三态验签（Valid/Unsigned/Bad），安装向导（签名放行 / 未签名开发者门 / 篡改硬拒），已安装注册表 /etc/apps.conf 与开始菜单"已安装"分组；
- **.lykc 动态驱动装载**：容器格式 + 强制验签 + 故障域内入口调用 + 驱动注册（示例驱动与 mklykc 打包工具随公开仓发布）；
- **图形桌面**：窗口管理、任务栏、开始菜单、动画、矢量字体全 UTF-8 中文渲染；
- **系统软件十款**：终端、设置、文件管理器、任务管理器、注册表编辑器、计算器、时钟/日历、画图、记事本、桌面部件；
- **双应用格式**：原生应用与瞬应用的装载、签名校验、沙盒；
- **瞬应用生态**：瞬语言解释器（内核内建 no_std tree-walk，类 Python 子集，
  括号可选，自检 `0 1 2 3 4 13 shan-ok gfx-ok` 全绿）＋ **原生图形化 draw API**
  （cls/px/rect/line/text 直写 256×192 画布 blit 上屏，无第三方注解库，print
  输出保留）＋ Rust 编译型瞬应用（`bin:` 入口双轨验签装载，允许预编译提速）；
- **Shan IDE（可登录）**：编辑/语法检查/试运行/打包一体，打包门需开发者会话
  （userinfo.level≥100），验签参数页（SM2/Ed25519 切换 + dev id），原生应用
  工具链页（.lyx 构建→服务器签名→安装）；配套宿主工具链
  tools/sign_lyx.py / sign_lyap.py / shan_pack.py / lyx_build_app.ps1；
- **原生应用 ring3 装载链**：签名 .lyx 经 exec::ly_exec_lyx 装载，syscall
  exit 自检（ring3 全链：签名→验签→建址→iretq→用户代码→syscall 退出→回收）；
- **动画体验**：开机/关机动画短促非模态——只在真实加载阶段之间显示，加载完
  即被桌面覆盖，不阻塞用户（boot 阶段 spin 900K→10K，关机动画 6×20M→6×3M）；
- **蓝屏取证**：致命故障时在串口留下故障地址、地址空间根与栈现场，多核下同样有效。

规划中未实现的能力在第 6 节路线图中如实标注。

### 1.3 双仓分发与开源策略（最小可信集）

LYSOR 采用"双仓分发"，公开仓**只放最小可信集**，不是全部内核代码：

- **公开仓库**：架构白皮书与全部公开文档、内核最小可信基座（TCB）骨架、
  原生 SDK 与示例、工具链（无私钥）。**公开版代码与私有仓一致**（插桩除外）；
  隐私代码全部插桩——**公开版不用跑通是预期**，只保证代码来源一致可审。
- **私有仓库**：完整版——组件实现、图形桌面与应用、签名与部署体系、内部配置，
  是公开仓库的真超集。
- **红线**：私钥/证书种子/内部地址（`*.pem/*.key/d.hex/*priv*/*.seed`）任何仓
  禁止入库（.gitignore 已列）；插桩点逐条记录于 `docs/REDACTION_LOG.md`。
- 同步流程与分级见 `docs/PUBLIC_SYNC.md`（P0 可信集公开 / P1 核心去隐私化 /
  P2 隐私不公开 / P3 工作产物不入库）。

切分逻辑：最需要第三方审查的是基座契约与安全模型——公开可审、可验证、可复现；
组件实现与部署体系属于产品与商业层，以完整版形式发布。审查者验证安全核心，
用户获得完整产品，两者互不干扰。

## 2. 现有操作系统痛点

### 2.1 宏内核（Linux 为代表）

宏内核把驱动、文件系统、网络协议栈、安全模块全部放进内核态。

- **可信基座无边**：数千万行代码全部处于最高特权级，任何一个驱动的空指针都可能拖垮整机。安全分析无法收敛，形式化验证在工程上不可能。
- **故障域重叠**：没有组件边界。子系统之间共享地址空间、共享栈、共享全局状态，一损俱损。
- **密码栈以补丁形式耦合**：加密算法散布在内核各处（磁盘加密、网络、签名校验各自为政），合规审计与算法替换极其困难，国密等本地化算法长期以第三方补丁形态存在。

### 2.2 微内核（seL4、MINIX 为代表）

微内核把服务全部推到用户态进程，内核只剩 IPC 与调度。

- **调用开销结构性偏高**：每一次"绘制一个矩形""读取一块数据"都要跨进程消息往返，上下文切换与消息拷贝的成本在高频路径（图形、存储）上尤其显著。这也是为什么大量实践最终把 GPU、存储驱动又迁回内核——微内核的理想在实践中不断向宏内核妥协。
- **可验证但无生态**：数学上被证明安全的系统（如 seL4）几乎没有应用生态，验证成果无法转化为可用产品。
- **开发门槛高**：服务外置要求开发者理解进程间通信模型，普通应用开发者难以参与底层生态。

### 2.3 传统混合内核（Windows NT、Apple XNU 为代表）

混合内核的初衷是"微内核的结构 + 宏内核的性能"，但实践中：

- **混合名不副实**：NT 执行体与 XNU 的 BSD 层体量巨大，核心服务实际全部运行在内核态，可信基座并不比宏内核小多少。
- **组件不可选、不可替换**：图形栈、密码栈与系统版本绑定发布，用户无法禁用、审计或替换任何一个安全关键部件。
- **闭源不可审查**：外部研究者只能依赖黑盒逆向，安全社区无法参与核心验证。

### 2.4 共同空白

三种架构都缺少同一个能力——*把"性能敏感的子系统"放进内核提速的同时，仍然保持它的可选性、故障隔离与可审计性*。这正是 LYSOR 组件化混合内核的切入点。

## 3. 核心架构：组件化混合内核模型

### 3.1 一句话定义

**内核只保留最小可信基座；一切可以独立存在的子系统——图形、密码学、未来的文件服务、网络服务——都以"内核组件（KC）"的形态运行在内核内，各自拥有私有栈与独立故障域，通过统一调用机制与基座交互，由持久化策略决定启用与否。**

### 3.2 三层模型

系统自上而下分为三层，边界清晰：

- **用户态/外壳层**：桌面外壳、窗口管理、系统软件、终端。应用进程运行在 ring 3、拥有硬件级独立地址空间；所有绘制统一经过图形组件间接完成，任何用户态代码不直接触碰帧缓冲。
- **内核组件层（KC）**：可选内核组件驻留内核，各自拥有私有动态栈与独立故障域。组件的启用与禁用由持久化策略决定、**下次重启生效、禁止热插拔**；组件故障的处置链路为"捕获 → 禁用 → 重启加载器 → 持久化"。基座不因组件缺陷停机。
- **最小可信基座（TCB）**：中断与异常分发、抢占式调度、物理/虚拟内存管理、双通道 IPC、系统调用入口、块设备抽象。规模刻意压到可人工审读、可形式化验证的量级——组件代码量再大也不进入基座。

### 3.3 与三种架构的本质区别

| 维度 | 宏内核 | 微内核 | NT/XNU | **LYSOR** |
|------|--------|--------|--------|-----------|
| 可信基座 | 无边 | 最小 | 接近宏内核 | **最小** |
| 子系统运行位置 | 内核态，无边界 | 用户态进程（跨进程调用） | 内核态，无边界 | **内核内组件（同址直调）** |
| 调用性能 | 高 | 低（消息往返） | 高 | **高（同址直调）** |
| 故障隔离 | 无 | 进程级 | 无 | **组件级故障域** |
| 子系统可选性 | 不可选 | 可选但生态难 | 不可选 | **全部可选，禁用即显式拒绝** |
| 密码栈 | 补丁耦合 | 进程服务 | 版本绑定 | **独立组件，双轨可审计** |
| 可验证性 | 不可能 | 可能（无生态） | 不可能 | **基座最小化，验证路径可行** |

### 3.4 核心创新点

**创新一：组件级故障域，替代进程级隔离的重量。**
每个组件拥有自己的私有动态栈（仅在组件启动时按需分配），组件内部发生的异常被内核基座捕获并归因到具体组件，按策略处置——组件被禁用、锁定，重启加载器后系统继续运行。这获得了接近微内核的故障隔离，却不需要跨进程消息的开销。

**创新二：策略治理，拒绝热插拔。**
组件的启用与禁用由持久化策略文件决定，修改在下次重启生效。这是有意为之的取舍：运行时插拔组件带来状态一致性与安全的双重风险，"重启生效"用极小的灵活性代价换来了确定性的系统状态。组件故障后的处置全部由基座在普通上下文完成，不依赖异常处理路径写盘。

**创新三：失败即拒绝（fail-closed），全链路无静默放行。**
安全关键路径上不存在"组件不可用就跳过校验"的旁路。签名验证组件未加载时，验证请求被显式拒绝，而不是默认放行。整个系统中不存在"保护桩"——所有安全语义要么真实验证，要么明确拒绝。

**创新四：最小基座即验证路径。**
基座只包含上文列出的最小集合，规模刻意压到可人工审读、可形式化验证的量级。所有安全分析、第三方审查、形式化验证只需聚焦基座——这是与"宏内核无边"的根本分界。

### 3.5 驱动即组件 + 开放端子

驱动是系统里最接近硬件的"不可信代码"：寄存器操作、DMA 与中断处理都是经典缺陷温床。传统内核把驱动编死在基座里，缺陷直接扩大可信计算基；LYSOR 让**驱动以内核组件（KC）形态运行**，与密码栈、图形栈共享同一套组件治理：私有动态栈、独立故障域、持久化策略、fail-closed 处置。

在此基础上 v0.2 开放"驱动端子"（Open Driver Endpoint）：

- **容器化**：第三方驱动以 `.lykc` 容器发布，固定基址链接、段布局平铺，装载即验签——**无签名或验签失败一律硬错误，无对话框、无旁路**，与 KC 路径口径一致；
- **唯一调用面**：`.lykc` 驱动不引用任何内核外部符号，一切能力（帧分配、页映射、MMIO、PCI 配置、中断登记、日志、DMA）经入口参数传入的 `LyKernelExports` 导出表获得，ABI 版本不符即拒绝；
- **故障域内调用**：模块入口、probe、start、ioctl 全部经 KC 机制在私有栈上执行，异常由基座归因处置；
- **可审计边界**：驱动描述符（名称/总线/类/ABI）以内核副本为准，注册进驱动管理器后按类查询、路由调用——开放端子是"基座可审、组件可换"原则向驱动层的外推。

## 4. 关键子系统概述

### 4.1 双通道 IPC

传统系统只提供一种进程间通信原语，迫使所有场景共用同一套信任与性能模型。LYSOR 按场景分成两条独立通道：

- **通道一：消息端口（拷贝式）**。有界环形队列传递固定大小消息，发送方拷入、接收方拷出，互不共享内存。适合控制面：命令、事件、短通知。无共享状态、无数据竞争面、语义简单可推演。
- **通道二：共享内存（白名单授权）**。零拷贝的大块数据交换区。每块共享区附带显式访问白名单与审计日志：不在名单内的访问者被明确拒绝并记录在案，绝不静默放行。适合数据面：帧缓冲、大文件缓冲、高频采样。

设计逻辑：控制面用最简单可靠的机制保证正确性；数据面用最高吞吐的机制保证性能；两者的信任边界由白名单与审计独立把守。

### 4.2 安全密码栈

**信任模型**：内核持有开发者公钥证书表，所有可执行内容装载前强制验签；验签失败拒绝装载，无签名不等于放行。生产签名在离线签名服务器完成，私钥永不进入内核、构建机与代码仓库；证书支持注册与吊销，泄露可即时止损。

**双轨算法，国密优先**：国密系列（SM2 签名 / SM3 摘要 / SM4 分组）为第一轨；Ed25519 与 SHA-512 为备用轨。双轨并存、运行自检，任一轨自检失败即该轨不可用且显式拒绝。

**密码栈为什么必须是可选组件**：几乎所有系统的密码能力要么编译死在内核里，要么作为不可替换的系统库绑定发布——合规环境无法独立审计密码实现，算法升级被迫跟随整个系统版本，密码缺陷的影响范围无法隔离。LYSOR 把整套密码能力放进独立内核组件：可禁用、可替换、可审计，故障域独立，自检失败时全系统进入"显式拒绝"状态而不是退化为无保护运行。

**应用侧权限模型**：应用默认零权限，网络、存储写入等能力须在清单中显式声明，装载时校验，运行期不可提升。瞬应用在此基础上进一步收缩：无持久化、有沙盒、生命周期随用随弃。

### 4.3 双应用生态

LYSOR 同时支持两类应用形态，对应两种信任与生命周期模型：

- **原生应用**：编译型语言（Rust 等）编译为系统原生格式，安装后持久存在，
  可使用全部系统能力。装载前强制双轨验签（SM2 国密优先 / Ed25519 备用）。
  适合性能敏感、功能完整的桌面软件。**不支持瞬语言**；运行时依赖必须随包打包。
  运行在 ring3 高区（`USER_BASE` 起，独立页表根）；代码 PIC（RIP-relative），
  数据指针由打包器按 ELF `.rela` 重定位加 `USER_BASE`——链接基址 0，杜绝
  static 模型的绝对地址裸偏移（契约细节见开发指南 §1.1）。
- **瞬应用**：以 `.lyap` 包为单位即时装载，**点开即用、无需安装、最多预编译**。
  界面用**原生图形化 draw API**（直写画布 blit 上屏，无第三方注解库），
  逻辑与界面同源（`print` 命令行输出保留）。运行在沙盒目录中，权限最小化。
  **跨语言**：瞬语言（解释型，内核内建）/ Rust（编译型 `bin:` 入口）/
  JS/TS（规划，轻量 MIT 引擎）。适合轻量工具类程序。

设计意图：原生应用保证生态上限（系统能做什么它就能做什么），瞬应用保证安全
下限（不受信代码的伤害半径被压到最小）。两者共享同一套图形与系统能力底座，
开发者按信任级别选择形态。工具链：宿主构建（lyx_build_app.ps1）+ 服务器签名
（sign_lyx/sign_lyap）+ Shan IDE 一体化编辑/打包。

### 4.4 图形系统与桌面

- **唯一渲染出口**：应用——包括系统桌面自身——被禁止直接写帧缓冲，所有绘制统一经过图形组件完成。传统系统中"任何内核/驱动代码都能覆写屏幕"导致的信息泄露与绘制混乱，从架构上被排除。
- **矢量字体引擎**：内嵌开源授权（SIL OFL 1.1）的矢量字体，全 UTF-8 覆盖，中文渲染为第一公民，无位图字体的缩放锯齿问题。
- **动画体验（短促非模态）**：开机/关机/窗口动画学习 Windows/macOS 的克制——
  开窗缩放 8 tick（≈80ms）、开始菜单滑入 8 帧、启动阶段只在真实加载之间显示
  并立即被桌面覆盖（不 spin 阻塞）；关机动画降为短促淡出。原则：**动画不抢占
  主要任务、不阻塞用户**——加载动画只在"真正加载时"显示，加载完成即清除。

### 4.5 存储与资源管理

- **LFS 文件系统**：自研轻量文件系统——连续分配换取顺序读写性能，每个文件节点带校验，权限位内建；不引入日志等重型机制，代码量与攻击面同步最小化。磁盘格式规范公开可审查（见蓝皮书）。
- **真盘持久化**：从真实块设备挂载根分区，跨重启持久化经过多轮实测验证（计数器递增、文件往返、目录完整）。
- **自适应资源分配**：内存不写死。系统按启动参数、固件接口、硬件寄存器的优先级逐级探测可用内存；组件栈按需分配、注销归还——同一份内核可运行于从小内存虚拟机到大内存物理机的不同环境。

### 4.6 进程隔离与多核调度

- **硬件级进程隔离**：每个应用进程拥有独立页表根，内核切换时更换页表基址寄存器；内核区域对用户代码不可见；应用代码运行在最低特权级。
- **SMP 多核**：每个 CPU 拥有独立运行上下文（任务状态段、局部描述符、本地中断控制器与本地存储），核间中断驱动各 CPU 的调度 tick，内核共享结构以自旋锁保护；线程可绑定 CPU 亲和性，负载按亲和性两遍扫描分配。多核 4 核实测全部在线并行，单核运行无回归。

### 4.7 可观测性

- **串口日志**为第一调试通道，系统各阶段（引导、内存、调度、组件、签名）全链路留痕；
- **系统终端**提供真实命令集（文件操作、进程查看、组件查询），系统状态可随时在机内核查；
- **任务管理器 / 注册表编辑器 / 文件管理器**全部读取真实内核数据（真实线程表、真实配置树、真实目录），无演示假数据。

### 4.8 IQCL 账号体系与开发者识别

v0.2 引入 IQCL 账号登录（设备码 OAuth 轨道），与本地账户（root/user，无密码，开发用）并存：

- **登录屏**在桌面启动前呈现：本地账户直达；IQCL 账户进入设备码流程——展示 `user_code` 与 `verification_uri`，按服务端 `interval` 轮询 token，拉取 `userinfo` 完成登录；
- **会话持久化**：refresh_token 存 `/var/auth/session`（LFS 真盘），重启免重登（30 天有效，轮换保存）；
- **开发者识别**：`userinfo.level ≥ LY_DEV_LEVEL(100)` 即标记该会话为开发者——安装签名门对"未签名应用"只对开发者会话放行（E 项口径），KC/.lykc 路径无此开关，硬错误；
- **过渡性质**：v0.2 联调用明文 HTTP（Cloudflare 对 `/api/yggdrasil/oauth2/*` 放行）；内核 TLS 1.2 客户端已实现（冒烟 E2E 通过），浏览器 https 接线与全站强制 HTTPS 列入下一步；浏览器侧授权仍走 https 不受影响。

## 5. 设计取舍、已知局限

### 5.1 优势

1. **同址性能 + 组件隔离的兼得**：高频图形调用没有跨进程开销，组件崩溃又不拖垮基座。
2. **每进程硬件级地址空间隔离**：应用越权的防线是硬件分页，不只是软件检查。
3. **可信基座真正最小**：安全分析与形式化验证只需聚焦基座，组件再复杂也不扩大基座。
4. **密码栈合规友好**：双轨可选、可审计、可替换，国密优先且标准号明确。
5. **全链路 fail-closed**：无保护桩、无静默降级，安全语义可推演。
6. **确定性的组件治理**：重启生效换取状态一致性，系统行为可预测。
7. **双生态的安全分层**：不受信代码被瞬应用沙盒压缩伤害半径，受信代码有完整能力。

### 5.2 短板与局限（如实陈述）

1. **组件级隔离弱于进程级隔离**：内核组件与基座同地址空间，越权访问的防线是权限授权、故障域与策略治理，而非硬件页表强隔离（应用进程已有硬件级隔离）。强隔离需求场景（多租户、恶意代码密集）应使用瞬应用沙盒，或等待规划中的组件进程化隔离模式。
2. **禁止热插拔的代价**：组件变更必须重启，牺牲运行时灵活性换取一致性——对长运行场景这是取舍而非缺陷，对需要热升级的场景是实际限制。
3. **生态从零起步**：应用格式、工具链均为自研私有标准，第三方迁移成本存在；靠公开规范与蓝皮书降低接入门槛，但不回避生态冷启动的现实难度。
4. **外设覆盖有限**：网络栈已实现 e1000 网卡驱动与 ARP/IPv4/ICMP/UDP/DNS/TCP/HTTP/TLS 1.2 客户端协议栈（TLS 端到端冒烟通过，浏览器 https 接线待下一步）；**Intel 显卡驱动覆盖范围待真机验证**（QEMU std-vga 实测通过）；声卡、蓝牙、网络文件共享未实现；当前版本定位为图形桌面工作场景而非全场景通用系统。
5. **输入路径的实证边界**：键盘路径完整实证；鼠标点击/拖动代码已落地，但真机路径待验证（无头虚拟机环境存在注入限制）。
6. **服务框架先行**：init 服务管理、登录认证、资源限额、计划任务、时间同步、设备管理等当前为框架占位，正式实现列入路线图。

## 6. 发展路线图

### 6.1 里程碑回顾（已完成）

内核基座 → 图形桌面与系统软件 → 真盘持久化 → 每进程独立地址空间（ring 3）→ SMP 多核调度（4 核实测）。各阶段均以启动实测与跨重启持久化验证为收口标准，详见第 1.2 节清单。

### 6.2 规划中（如实标注，未实现）

- **浏览器 https 接线**：内核 TLS 1.2 客户端已实现（冒烟 E2E 通过），浏览器替换 TLS_HTML 占位页、证书加载 `/etc/tls/`、全站强制 HTTPS 为下一步；
- **DHCP**：静态配置向自动获取演进（当前 QEMU user-net 固定地址）；
- **服务端监听套接字**：TCP 当前为客户端为主，服务端监听列入规划；
- **用户态服务正式化**：init 服务管理、登录认证、资源限额（cgroup）、计划任务、时间同步、设备热插拔由框架进入正式实现；
- **内核内存分配器演进**：SLAB 分配器优化小对象路径；
- **组件进程化隔离模式**：为强隔离需求提供可选的进程形态运行方式；
- **系统软件增强**：窗口缩放与多窗口并发、分辨率/亮度热切换；
- **声卡、蓝牙、网络文件共享**。

### 6.3 版本与文档同步约定

白皮书文档版本（wp-vX.Y.Z）随系统版本（vX.Y.Z）同步演进；蓝皮书不得与本文冲突；发现矛盾时以本文为基准并修订周边文档与实现。

LYSOR OS 不试图在 Linux 的路上做得更好，而是回答一个更根本的问题：**操作系统的性能敏感部分与安全关键部分，能否不再互斥？**

组件化混合内核给出的答案是：基座小到可以验证，组件快到没有跨进程开销，安全语义全部 fail-closed，密码栈可审计可替换，应用生态按信任分层。每一个取舍都明确写出——包括短板。
